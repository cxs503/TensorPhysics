## 2. R1 复核明细（physics contracts）

### 2.1 溯源三态 —— 已证实

`ReferenceBand.__post_init__` 把 `provenance` 约束为三值闭集，并对 `WITHHELD` 追加禁锚规则：

```
physics_contracts.py:85   if self.provenance not in ("EXPERIMENTAL", "DERIVED", "WITHHELD"):
physics_contracts.py:90   if self.provenance == "WITHHELD" and self.admissible_for_judgment:
physics_contracts.py:95   if self.tolerance_rel <= 0:
```

- 已证实：非法字符串、`WITHHELD+admissible`、非正容差三者都在**构造期**失败（fail-at-construction），
  与设计文档 `docs/physics_contracts.md:18-19` 一致；单测 `tests/test_physics_contracts.py:121-124` 覆盖。
- 已证实（正面）：`wetted_surface.axisymmetric_empirical` 真的使用了 `admissible_for_judgment=False`
  把 +50.6% 偏差的实证参考降级（`physics_contracts.py:280-282`），说明该字段不是装饰。

### 2.2 WITHHELD 禁锚 —— 已证实可绕行（缺陷 D2）

禁锚规则只挂在 `ReferenceBand` 的构造器上，而 `PhysicsModelContract.__post_init__`
（`physics_contracts.py:110-130`）**从不校验 `references` 的元素类型**。探针实测：

```json
dict_reference_accepted = true   # references=({"provenance": "WITHHELD", "admissible_for_judgment": True, ...},)
读回 provenance = "WITHHELD" -> 注册成功, 禁锚失效
```

即：一张 provenance 标成 `WITHHELD`、却声明可作判定锚的引用，只要以 **dict 或鸭子对象**形式传入，
就能成功注册——审计 m2087 要"不可表示"的那个失败模式，仍然可表示。结论：**已证实**（缺陷，P2）。

### 2.3 零锚契约合法注册（缺陷 D3）

`references` 默认 `field(default_factory=tuple)`（`:106`），且没有"至少一条可判锚"的校验。实测当前 5 个
注册契约的可判锚数量：

| 契约 key | 参考带总数 | 可判锚数 |
|---|---|---|
| `resistance.suboff_shared_core` | 2 | 2 |
| `resistance.holtrop1984_full` | 0 | 0 |
| `friction.ittc1957` | 0 | 0 |
| `friction.schoenherr1932` | 0 | 0 |
| `wetted_surface.axisymmetric_empirical` | 2 | 1 |

其中 `resistance.holtrop1984_full`、`friction.ittc1957`、`friction.schoenherr1932` 三条**零参考带**却注册成功
（探针：`can_register_without_anchor = YES`）。最要紧的是被
命名为 "full method" 的 `resistance.holtrop1984_full`（468 行 Holtrop 核）**一条验收锚都没有**，
其正确性在契约层是**未验证**的。结论：**已证实**（缺陷，P2）。

### 2.4 命名门 —— 部分生效（缺陷 D1）

门实现是指**字面字符串匹配**：

```
physics_contracts.py:115   is_hm_name = "holtrop" in label and ("mennen" in label or "hm1984" in label
physics_contracts.py:117   if is_hm_name and not _HM1984_REQUIRED_ROLES <= roles:
```

探针（同一套 SUBOFF 组件，只换名字）：

| declared_method | 门行为 |
|---|---|
| `Holtrop & Mennen (1984) full method` | 拒绝 |
| `Holtrop-Mennen simplified` | 拒绝 |
| `Holtrop 1984 wave-resistance method` | **放过** |
| `Holtrop (1984) method` | **放过** |

"**Holtrop 1984 wave-resistance method**" 这种完全等价于完整 Holtrop 声明的名字被放过 → 同一类
错标签仍有可表示路径。结论：**已证实**（缺陷，P2）。修法极小：把判据换成"标签含 holtrop 即必须
满足 `_HM1984_REQUIRED_ROLES`"（去掉词元白名单），或反过来用 `components` 的 role 集合做**充分且
必要**的双向校验。

### 2.5 声明 ≠ 实现（缺陷 D4）

`reference_kernel` 只是一条点分字符串，`__post_init__` 仅检查非空（`:127-128`）；没有任何代码
`importlib` 解析它、也没有校验 `MethodComponent` 的 role 是否真有对应实现。因此"完整 Holtrop 组件集"
可以靠**四个 self-declared 字符串**伪造成立，回归时也无人发现核函数被删。结论：**已证实**（代码读
证据；缺陷 P2）。

### 2.6 alias 可覆盖契约 key（缺陷 D5）

`register()` 只查 alias↔alias 冲突（`:139-150`），`get_contract()` 先查 alias 再查 key（`:153`）。
探针：给某契约注册 alias `"friction.ittc1957"` 之后，`get_contract("friction.ittc1957")` 返回的是
**`probe.alias`**（新契约），旧的正式 key 被静默遮蔽。结论：**已证实**（缺陷，P3；
当前 5 个契约的 alias 集合无此冲突，属潜在雷）。

### 2.7 判定路径未接线（缺陷 D6 —— R1 的 P1）

在生态内全量 grep `physics_contracts` / `admissible_for_judgment`：命中只有
`tests/test_physics_contracts.py`（单测）与 `physics_kernels_resistance.py` 的 docstring 提及；
**`TensorPlatform` 仓 0 命中**。`docs/physics_contracts.md:36-41` 把消费义务写成"TP acceptance code
MUST resolve ... read references with admissible_for_judgment=True only"，但该 acceptance code
并不存在/未引用本表。结论：**已证实**（缺陷 D6，P1）：R1 交付的是**声明层**，禁止性规则（WITHHELD
禁锚）在当前代码里只对"走正规构造器的人"生效，对真正的判定动作没有任何约束力。这也是本报告给出
PARTIAL_PASS 而不是 PASS 的主因。

### 2.8 SUBOFF-01 锚的可信度（缺陷 D7、D8）

契约里的两条锚（`physics_contracts.py:196-201`）与本报告复算：

| 量 | 契约/复算值 | 说明 |
|---|---|---|
| DERIVED 锚 `ct` | `0.003461889103159` | tol `1e-09`；注释称"6 个受审核 bitwise 一致" |
| 参考核复算 `ct` | `0.0034618891031589` | 与锚相对偏差 `1.25e-16` —— 因为**同一个公式**，属**同义反复** |
| EXPERIMENTAL 锚 `ct` | `0.0038` | tol `0.15`；**无引文**（`ReferenceBand` 无 citation 字段，见下） |
| 核 vs EXPERIMENTAL | 相对误差 `8.90%` | <15% 容差 → 通过；但 **>3%** 报告纪律线 |

`ReferenceBand` 的字段全集（探针读回）：`admissible_for_judgment, case_id, provenance, quantity, tolerance_rel, unit, value`——**没有**
引文/来源字段、**没有**案例输入（L/B/Cb/V/ν/S）字段。后果两条：

1. **D7（P2）**：EXPERIMENTAL 锚无法核验来源，"EXPERIMENTAL" 这一档的语义实际上只由注册者自律维持；
   审计 m2087 判 `WITHHELD` 的依据是"来源不可核"，而这里**有来源字段的缺失**，等于把同样的风险从
   provenance 枚举挪到了字段外。
2. **D8（P1）**：案例输入只活在**测试文件的 docstring**（`tests/test_physics_contracts.py:41-51`：
   L=4.356, B=0.508, Cb=0.542, V=3.0, ρ=998.2, ν=1.004e-6, S=4.417911），契约里没有 case 记录。

几何未先验的定量后果（本报告实测）：用文献排水体积 `0.7008 m³`（**推测值，仓内无此记录**）与箱
形基 `L·B·T` 反算 `Cb = 0.6234`，与契约使用的 `Cb = 0.542` 相对偏差 `13.1%`；
在该 Cb 下核的 `ct = 0.0035083548931135`，相对契约值变化 **`1.34%`**，即
**`1.3e+07` 倍**于 DERIVED 锚容差 `1e-09`。换句话说：这个 1e-9 的"硬锚"把
一个**未经几何验证**的 Cb 冻结成了不可协商的判据——锚越紧，未验证输入越危险（图 2 右）。

## 3. R3 复核明细（platform reporting 接线）

### 3.1 terminal-only 语义 —— 已证实

`research_runner.py:100-112`（SUCCEEDED）与 `:135-140`（终态 FAILED）两处调用
`_register_platform_outcome`；`_retry_or_fail` 内以 `if target is TaskStatus.FAILED:` 设闸
（`research_runner.py:136-138`），RETRY_WAIT 不注册。本报告探针事件流印证：

- 成功路径事件序列：`task_created → worker_claimed → agent_started → agent_completed → validation_passed`；正常注入 FakeRegistry 时末尾追加
  `platform_registration / succeeded → succeeded`（见 3.3），而注册抛异常的场景下该事件**缺失**
  （`platform_event_present = False`，正是缺陷 D10 的现场）。
- 单测 `test_platform_reporting.py:145-176` 覆盖 "非终态不注册" 与 "WAITING_INPUT 不注册"。

结论：语义符合边界裁定（reporting 而非 gating 的**意图**），**已证实**。

### 3.2 终态落盘不只在 runner：崩溃恢复与 worker 取消均漏报（缺陷 D11）

`ResearchTaskStore.recover_interrupted()`（`research_runtime.py:303-329`）在重启后把 CLAIMED/
RUNNING/VERIFYING 任务直接置为 RETRY_WAIT 或 **FAILED**，只写 `task_recovered` 事件，**不调用**
`_register_platform_outcome`（store 层根本不持有 registry）。探针（`max_attempts=1` 崩溃）：

```json
{"terminal_status": "failed", "events": ["task_created", "worker_claimed", "agent_started", "task_recovered"], "platform_event_present": false}
```

即平台账本对"因崩溃而终态失败"的 run 永远空白，且账本侧无从区分"没跑过"与"跑了但崩了"。

同一类洞还有第三条路径：`worker.py:142`（拒绝越界 workspace）与 `worker.py:159`（非法 plan）**直接**
把任务落为 `CANCELLED`，同样不经过 runner。探针（`QUEUED → CANCELLED`）：

```json
{"status": "cancelled", "events": ["task_created", "unsafe_workspace_rejected"],
  "platform_event_present": false}
```

根因是**接线位置**：R3 的 diff 只改了 `research_runner.py` 与 `research_runtime.py`，把"终态注册"实现
成 **runner-局部** 动作；而终态是可以由 store/worker 层直接写出的（`transition()` 是公开 API），因此
凡不经 runner 的终态天然在覆盖之外。结论：**已证实**（缺陷，P2）。修法：把注册动作从 runner 上移到
"终态观测点"（`transition()` 落终态后的统一 post-hook，或调用方订阅 `list_events` 的终态事件），
使覆盖与"谁写的终态"无关。

### 3.3 append_event —— 可用，但写入自环伪转移（缺陷 D9）

`append_event`（`research_runtime.py:349-370`）在同一 `BEGIN IMMEDIATE` 事务里追加事件、不改任务
状态，异常回滚——这部分**已证实健壮**（单测 `:178-190` + 探针）。但 `:366` 传的是
`self._event(task_id, status, status, ...)`，于是事件行 `from_status == to_status`：

```
("platform_registration", "succeeded", "succeeded")
```

任何"由 (from,to) 重建状态机"的消费者都会看到一次**不存在的自转移**（SUCCEEDED→SUCCEEDED 在
`_ALLOWED` 里根本不合法，只是事件表没有 CHECK 约束所以写得进去）。结论：**已证实**（缺陷，P3；
建议非转移事件 to_status=None 或单独 event 表）。

### 3.4 "只报告、永不 gate" 不变式被打破（缺陷 D10 —— R3 的 P1）

`platform_reporting.py` 的 docstring 声称 "this module never raises"，其保证来自
`except (PlatformRegistryError, ValueError)`（`platform_reporting.py:50`）。实测两个反例：

1. **注入式**：registry 抛 `RuntimeError` / `OSError` / `KeyError` → 直接逃逸（
   `never_raises` 探针：`ValueError→failed`，`PlatformRegistryError→failed`，
   `RuntimeError→RAISED RuntimeError`）。`ResearchTaskRunner.__init__` 把 `platform_registry` 声明为
   `Any`（`research_runner.py:32-36`），注入是官方用法，故这条路径是**契约内**的。
2. **内置客户端**：`TensorPlatformRunRegistry.register` 在 `Request(...)` 构造处（`platform_registry.py:112-121`）
   **位于 `_read_json` 的 try 之外**；`base_url` 只要 `startswith("http")` 就通过构造期校验，若 URL
   含空格（如 `TENSORPLATFORM_URL="http://ship api:8001"` 这类笔误），逃逸出的是
   `http.client.InvalidURL` —— 它**既不是** `ValueError` 也**不是** `OSError`。探针输出：

```
ESCAPED: http.client.InvalidURL | is ValueError: False | is OSError: False | is HTTPException: True
```

后果（探针全链路复现）：注册抛错发生在 `research_runner.py:106-108`，而该调用位于
`try:`（`:99`）内，外层 `except Exception`（`:114`）会走 `_retry_or_fail(expected_status=VERIFYING)`，
可此时任务**已经是 SUCCEEDED**：

```json
{"run_once_raised": "InvalidTaskTransition: task task-p1 is succeeded; expected verifying", "task_status_after": "succeeded",
  "platform_event_present": false}
```

也就是说：**一次报告失败，让一个已经成功的任务对外表现为异常**，并且连带丢掉 `platform_registration`
事件（`append_event` 的反异常保护根本轮不到）。这正好违反 R3 的核心裁定"reporting never gates"。
结论：**已证实**（缺陷 D10，P1）。

生产表现（读代码确认）：`InvalidTaskTransition` 继承自 `ResearchRuntimeError(RuntimeError)`
（`research_runtime.py:20-27`），**不是** `ValueError`，所以 `worker.py:156` 的 `except ValueError`
接不住，落到 `worker.py:162` 的 `except Exception: LOG.exception(...)`——现场表现是"任务在库里已
succeeded，日志报 Failed to process task，平台账本没有这一条 run"。结论：**已证实**（类层次 + 探针）。

最小修法（两处、各一行级）：① `platform_reporting.py:50` 改成 `except Exception`（保留
`logger.warning` 与 `{"outcome": "failed"}` 记录）；② `research_runner.py:99` 的 `try` 只包住
validator 与状态转移，把 `_register_platform_outcome` 挪到 `try` 之外（或用独立 try 包裹）。

## 7. 注意点 / 局限

1. **未验证项**：真实 TensorPlatform 端点（`POST /api/v1/tensorphysics/runs`）的往返行为——本环境
   无 `TENSORPLATFORM_URL` 令牌，故 §3 的"registered"结论仅在 FakeRegistry 层面成立；真实 HTTP 只
   验证了 `InvalidURL` 逃逸这一异常分支。→ `未验证`。
2. **推测项**：SUBOFF `Cb = 0.542` 的来源（推测为受审平台存储值）；文献排水体积 `0.7008 m³` 为记
   忆值，仓内无工件。二者只用于**敏感性量级**论证（第 4 行误差），不改变"案例输入未入契约"这一事实判断。
3. **未覆盖**：`physics_kernels_holtrop1984.py`（468 行）内部实现的正确性未复核——契约表不给它锚，
   本复核也无可对基准；建议单独开复核单（需 Holtrop 1984 原始回归算例）。
4. **只读约束**：按任务纪律未改 `src/`；所有缺陷只给最小修法建议，未实施（本单产出=报告+探针+图）。
5. **图 1-3 的解释边界**：均为**系数级**证据，不含流场云图——本任务是契约/接线复核，无场量计算，
   故无云图可出（理由显式声明，非遗漏）。
