# Adapter Inventory

> Scope: `src/tensorphysics/adapters/` only. Generated by reading
> `adapters/__init__.py`, `adapters/tensordem.py`, `protocols.py`, and the
> `tests/` suite. No source code was modified.

## 1. How adapters are discovered

The orchestration core talks to specialist solvers through the
`Solver` Protocol defined in `src/tensorphysics/protocols.py`:

```python
@runtime_checkable
class Solver(Protocol):
    @property
    def name(self) -> str: ...
    def initialize(self, context: SolverContext) -> None: ...
    def advance(self, context: SolverContext) -> None: ...
    def finalize(self, context: SolverContext) -> None: ...
    def snapshot(self, context: SolverContext) -> SolverState: ...
```

`SolverContext` carries `step`, `time`, `dt`, and a `metadata` mapping.
`SolverState` is a dataclass envelope (`solver_name`, `step`, `time`,
`payload`, `schema_version`) that the protocol declares as the return type
of `snapshot`.

The `adapters/__init__.py` package re-exports exactly one adapter:

```python
from .tensordem import TensorDEMAdapter
__all__ = ["TensorDEMAdapter"]
```

A directory listing of `src/tensorphysics/adapters/` confirms there are only
two files: `__init__.py` and `tensordem.py`. **There is exactly one adapter
in the ecosystem: `TensorDEMAdapter`.**

## 3. Per-adapter detail: `TensorDEMAdapter`

**Target solver:** the 2-D `IceDEM` stepping API from the optional
TensorDEM package. The adapter never imports PyTorch; the caller constructs
the native `IceDEM` instance and passes it in, keeping TensorPhysics core
dependency-free.

### Capabilities present

- **Construction validation.** Rejects non-string/empty `name`,
  non-finite or negative `time_tolerance`, models without a callable
  `step()`, and models missing `dt`/`time` attributes.
- **`initialize`.** Checks the native `dt` is finite and positive, and that
  the native `model.time` matches `context.time` within `time_tolerance`.
- **`advance`.** Requires the global `context.dt` to be an **integer
  multiple** of the native `dt`; otherwise raises
  `TensorDEMAdapterError`. Splits each global step into `n_substeps`
  native steps, requests loads from `load_provider` at every substep start
  (passing a sub-`SolverContext` with `substep_index` /
  `substeps_in_global_step` metadata), and calls
  `model.step(external_forces=loads, load_time=sub_time)`. After the loop it
  verifies the native clock landed on `context.time + context.dt`.
- **`finalize`.** Intentional no-op — the current IceDEM API needs no
  teardown.
- **`snapshot`.** Returns orchestration metadata: `adapter` class path,
  `native_time`, `native_dt`, `native_step_count`, `adapter_substeps`,
  `particle_count` (from `model.positions.shape[0]`), and
  `restartable=False`.

### Explicitly missing / unsupported

- **`snapshot` return-type conformance.** The `Solver` Protocol declares
  `snapshot -> SolverState`, but the adapter returns a plain
  `dict[str, Any]`. It does not wrap its payload in the `SolverState`
  dataclass, so it is structurally non-conformant with the declared
  protocol signature (though `runtime_checkable` only checks method
  existence, not return types).
- **Restart / restore.** `restartable` is hard-coded `False`. The docstring
  states full restart requires a native solver state/restore contract that
  does not exist yet.
- **Rollback on partial failure.** If a later substep fails, earlier native
  substeps are **not** rolled back; the partially advanced model must not be
  resumed.
- **3-D DEM.** Only the 2-D `IceDEM` API is adapted. There is **no**
  `DEM3DAdapter` in `src/tensorphysics/adapters/`, even though several
  research campaigns and benchmarks reference the protocol string
  `"tensordem-dem3d-three-point-bending-v1"` (see
  `tests/test_research_campaign_dem3d_timestep_refinement.py`,
  `tests/test_research_benchmark_dem3d_bending.py`,
  `tests/test_research_campaign_dem3d_load_sensitivity.py`,
  `tests/test_analyze_dem3d_load_sensitivity.py`). Those tests exercise
  report-gating / evidence logic on JSON artifacts, **not** a live 3-D
  solver adapter.
- **No other solver families.** No FEM, FDM, SPH, or continuum-field
  adapters ship under `adapters/`. (Field coupling in `tests/test_coupling.py`
  uses `CouplingContext` over `SolverContext` + a fields manager, not a
  dedicated adapter class.)

### Test coverage (`tests/test_tensordem_adapter.py`)

Three tests, all using a `FakeIceDEM` double:

| Test | What it proves |
|---|---|
| `test_tensordem_adapter_subcycles_and_requests_loads_at_each_substep` | 8 native substeps for 2 global steps of dt=0.1 over native dt=0.025; load provider called at every substep time; `external_forces` carry `substep_index`; snapshot reports `native_step_count=8`, `particle_count=3`, `restartable=False`. |
| `test_tensordem_adapter_rejects_nonintegral_global_step_ratio` | dt=0.1 vs native dt=0.03 raises `SimulationError` matching `"integer multiple"`; simulation state is `FAILED`; no native steps taken. |
| `test_tensordem_adapter_rejects_native_clock_drift` | Pre-seeded `model.time=0.01` vs simulation time 0.0 raises `SimulationError` matching `"does not match simulation time"`; state `FAILED`. |

**Not directly tested:** `finalize` (no-op, trivial), the `name` /
`time_tolerance` constructor validation branches, the post-loop end-time
drift check (distinct from the pre-loop drift check that *is* tested), and
the `snapshot` return-type mismatch against `SolverState`.

## 4. Summary — real coverage of the adapter layer

The TensorPhysics adapter layer is, at present, a **single-adapter
ecosystem**: `TensorDEMAdapter` for the 2-D IceDEM DEM solver. It implements
the full `Solver` lifecycle (`initialize` / `advance` / `finalize` /
`snapshot` plus `name`) and is the only adapter exported from
`adapters/__init__.py`. Its `advance` is genuinely non-trivial — integer
subcycling, per-substep load injection, and bidirectional clock-drift
guarding — and that core path is well covered by three focused tests.

However, real coverage is narrow in three dimensions:

1. **Solver breadth.** Only 2-D DEM is adapted. The repository's own
   research campaigns reference 3-D DEM bending/load-sensitivity protocols,
   but no `DEM3DAdapter` exists; those campaigns run against JSON evidence,
   not a live adapter. No FEM/FDM/SPH/continuum adapters ship either.
2. **Protocol conformance.** `snapshot` returns a bare `dict` rather than
   the `SolverState` envelope the `Solver` Protocol declares. This is a
   static-type / structural gap (invisible to `runtime_checkable`) that
   any future serialization or checkpoint consumer would hit.
3. **Lifecycle robustness.** Restart/restore is explicitly unsupported
   (`restartable=False`), partial-substep failure has no rollback, and
   several constructor-validation and post-loop drift branches lack
   direct unit tests.

In short: the one adapter that exists is solid and tested for its happy
path and two key failure modes, but the adapter layer as a whole covers a
single 2-D solver, does not yet conform to its own `snapshot` return type,
and has no restart or 3-D story despite the research layer already
referencing 3-D DEM protocols.
